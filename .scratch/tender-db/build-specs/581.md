### Decisions made here (none was open in the record; each is settled from it)

- **D581-1, twin repair: anchor on the kept twin.** Do not leave it out (skeptic D1 offered both).
  - `twin_repair_tx` writes `(emptied Tender, repair.keep)` for each drop that empties its Tender. The fold paths
    write from the Tender's own versions.
  - Why: the twins hold the same bytes, so the kept twin's Tender is the true successor. `null` keeps exactly one
    meaning ("retired before these records began"), which the docs can state truthfully.
  - The alternative left a repair-retired id at a permanent `410 []` (the as-designed INSERT…SELECT keyed on deleted
    notice ids), or at a `null` the docs would have to explain twice.
  - Cost: one `Option` parameter and a dozen lines.
- **D581-2, no successor cap.** The design said "cap 101", but the work is already bounded by the retired Tender's
  own version count: its ledger rows. A truncated list would misstate a split. `successors` is the complete distinct
  set, ascending.
- **D581-3, successors read without a join.** First `SELECT notice_id FROM retired_tenders WHERE retired_id = ?`.
  Then `SELECT tender_id FROM tender_versions WHERE caused_by_notice_id IN (…)` at `IN_CHUNK` width (512), deduped in
  a `BTreeSet`.
  - The IN read is the exact shape `guid_census_tenders_sql` already plan-gates as a `tender_versions_notice` seek at
    512 (guid_census.rs:110, gate at :1459).
  - Why not a join: turso's join-order traps (docs/agents/prod-box-reads.md, issues 417/421). This shape needs no
    planner trust.
- **D581-4, `Location` re-serialises the normalised `lang`** (`?lang=de` → `Location: /v1/tenders/<s>?lang=DEU`). No
  `RawQuery` extractor. The detail reads no other parameter, and `DEU` is an accepted spelling (api.rs
  `the_lang_selector_prefers_a_language_and_rejects_junk`).
- **D581-5, one body shape for both statuses:** `{"error":{"message":"tender retired","status":<308|410>},"successors":…}`.
  It keeps the one-shape error envelope. The field is not `merged_into`, because a retirement is not always a merge
  (design Q3).
- **D581-6, the null-case wording names no exact date:** "retired before these records began (October 2026)". This
  is true whatever day in October the deploy lands. If the deploy slips past 10-31, change the month in docs.rs,
  openapi.json and CHANGELOG.md.
- **D581-7, ledger parity is checked in three named ingest tests, not in `snapshot()`.** Adding it to `snapshot()`
  would put it in ~40 full-vs-daily comparisons. That is a wider blast radius than this unit needs, and those
  comparisons are about content.
- **D581-8, resolver order:**
  1. live (PK);
  2. ledger;
  3. the pre-ledger fallback: a `tender removed` change row AND `1 <= id <= sqlite_sequence('tenders')` (skeptic D2:
     the high-water, not `MAX(id)`).
  - Ledger rows always win, so an id retired after the deploy never reads as `null`.
- **D581-9, unchanged on purpose:**
  - the change feed (the byte-identity surface; design "SSE and feed");
  - `/v1/notices?tender=<retired>`, which stays 404;
  - `/v1/sql`'s allow-list (`retired_tenders` stays off it, the `org_merge_log` precedent; sql.rs denies by default,
    so sql.rs, a flip file, is not touched).

    /// `tender_versions` primary key the DELETE loop after it already walks. `Some` writes these

```rust
/// Where a Tender id's notices are now (issue 581).
///
/// A fold that regroups notices, or the twin repair, retires a Tender (`retire_chunk_tx`) and
/// records the notices it held in `retired_tenders`. A reader holding the retired id is answered
/// with the live Tenders those notices sit in NOW. So splits, chains (a successor retired later)
/// and a merge that is undone resolve with no hop limit, and the answer can move. That is why
/// the handler sends it `no-store`.
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum TenderResolution {
    /// The id is a live Tender.
    Live,
    /// The id was retired. These live Tenders hold at least one of its recorded notices,
    /// ascending and distinct. Empty when none does now.
    Retired(Vec<i64>),
    /// The id was retired before `retired_tenders` existed: a `tender removed` change row and an
    /// id within the layer's issued range, but no ledger row. Nothing says where its notices went.
    RetiredBeforeLedger,
    /// Never issued in this layer.
    Unknown,
}

/// The live probe: a primary-key seek.
const TENDER_LIVE_SQL: &str = "SELECT 1 FROM tenders WHERE id = ?";
/// A retired id's recorded notices, through `retired_tenders_id`.
const RETIRED_NOTICES_SQL: &str = "SELECT notice_id FROM retired_tenders WHERE retired_id = ?";
/// The Tenders holding `n` notices now, through `tender_versions_notice`: the IN shape
/// `guid_census_tenders_sql` plan-gates at [`IN_CHUNK`].
fn notice_tenders_sql(n: usize) -> String {
    format!("SELECT tender_id FROM tender_versions WHERE caused_by_notice_id IN ({})", placeholders(n))
}
/// The layer's Tender high-water, O(1) from `sqlite_sequence` (the `max_cursor` shape). Both
/// resets clear it, so an id above it was never issued in this layer (580 triage D2: not
/// `MAX(id)`, which a retired newest id would undercut).
const TENDER_HIGH_WATER_SQL: &str = "SELECT COALESCE((SELECT seq FROM sqlite_sequence WHERE name = 'tenders'), 0)";
/// A retirement in the change log, through `changes_entity (entity_kind, entity_id)`.
/// `retire_chunk_tx` writes the only `tender removed` rows, and the log is never trimmed.
const TENDER_REMOVED_SQL: &str =
    "SELECT 1 FROM changes WHERE entity_kind = 'tender' AND entity_id = ? AND op = 'removed' LIMIT 1";

/// Resolves a Tender id that `tender_detail` did not find (issue 581). In order: live; recorded
/// (`Retired`, even if no Tender holds the notices now); retired before the ledger; unknown.
pub async fn resolve_tender(conn: &Connection, id: i64) -> turso::Result<TenderResolution> {
    if exists(conn, TENDER_LIVE_SQL, vec![Value::Integer(id)]).await? {
        return Ok(TenderResolution::Live);
    }
    let mut notices = Vec::new();
    {
        let mut rows = conn.query(RETIRED_NOTICES_SQL, (Value::Integer(id),)).await?;
        while let Some(row) = rows.next().await? {
            notices.push(int(&row, 0));
        }
    }
    if !notices.is_empty() {
        notices.sort_unstable();
        notices.dedup();
        let mut successors = std::collections::BTreeSet::new();
        for part in notices.chunks(IN_CHUNK) {
            let params: Vec<Value> = part.iter().map(|&n| Value::Integer(n)).collect();
            let mut rows = conn.query(&notice_tenders_sql(part.len()), params).await?;
            while let Some(row) = rows.next().await? {
                successors.insert(int(&row, 0));
            }
        }
        return Ok(TenderResolution::Retired(successors.into_iter().collect()));
    }
    let issued = {
        let mut rows = conn.query(TENDER_HIGH_WATER_SQL, ()).await?;
        rows.next().await?.map_or(0, |row| int(&row, 0))
    };
    if (1..=issued).contains(&id) && exists(conn, TENDER_REMOVED_SQL, vec![Value::Integer(id)]).await? {
        return Ok(TenderResolution::RetiredBeforeLedger);
    }
    Ok(TenderResolution::Unknown)
}
```

- A successor is live by construction: a `tender_versions` row exists only for a live Tender, because
  `retire_chunk_tx` deletes both together. So there are no cycles and no hops.
- The transient full-path window: between Phase 2 and retirement, a notice can sit under two Tenders, and an earlier
  retired id can then briefly answer both. Covered by the docs' "for a moment during a fold".
- During a rebuild `tender_versions_notice` is deferred, but the ledger was just emptied, so no IN probe runs.

## 3. crates/app/src/v1/mod.rs: the `tender` handler (2007–2022)

```rust
/// `GET /v1/tenders/{id}` — one Tender in full.
///
/// An id a fold or a repair retired answers where its notices are now (issue 581): `308` to the
/// one Tender holding them, `410` naming several or none, `410` with `successors: null` for an id
/// retired before those records began. This is the issue-455 organization answer, with a list,
/// because a retirement can split. It is read when asked and can move (a merge that is undone), so
/// it is sent `Cache-Control: no-store`. Only an id never issued is a 404.
async fn tender(
    State(state): State<AppState>,
    ApiPath(id): ApiPath<i64>,
    ApiQuery(params): ApiQuery<Params>,
) -> ApiResult {
    // (keep the existing four-line `?lang=` comment)
    let lang = params.filter(store::now_unix())?.lang;
    let reader = state.readers.get().await?;
    if let Some(detail) = read::tender_detail(&reader, id, lang.as_deref()).await? {
        return Ok(axum::Json(json::detail(&detail)).into_response());
    }
    let body = |status: StatusCode, successors: Value| {
        json!({ "error": { "message": "tender retired", "status": status.as_u16() }, "successors": successors })
    };
    match read::resolve_tender(&reader, id).await? {
        read::TenderResolution::Retired(successors) if successors.len() == 1 => {
            let to = successors[0];
            // The normalised selector (`de` → `DEU`), an accepted spelling, so the followed
            // request picks the same language.
            let location = match &lang {
                Some(lang) => format!("/v1/tenders/{to}?lang={lang}"),
                None => format!("/v1/tenders/{to}"),
            };
            Ok((
                StatusCode::PERMANENT_REDIRECT,
                [(header::LOCATION, location), (header::CACHE_CONTROL, "no-store".to_owned())],
                axum::Json(body(StatusCode::PERMANENT_REDIRECT, json!([to]))),
            )
                .into_response())
        }
        read::TenderResolution::Retired(successors) => Ok((
            StatusCode::GONE,
            [(header::CACHE_CONTROL, "no-store")],
            axum::Json(body(StatusCode::GONE, json!(successors))),
        )
            .into_response()),
        read::TenderResolution::RetiredBeforeLedger => Ok((
            StatusCode::GONE,
            [(header::CACHE_CONTROL, "no-store")],
            axum::Json(body(StatusCode::GONE, Value::Null)),
        )
            .into_response()),
        read::TenderResolution::Live | read::TenderResolution::Unknown => Err(ApiError::not_found("tender")),
    }
}
```
