## 1. Decisions (made here, with reasons)

**D583-1. Remedy: stamp and re-queue the touched Tenders inside the merge's transaction. Do not
write rows in fold order.** This is 579 U4's remedy (d), taken from the dissolve path to the merge
path.
- Writing in fold order would mean deleting and re-inserting every row of each affected group:
  parties per (version, scope), bid parties per bid, and winners per version. The sort keys would
  be `Fact::Party`'s derived Ord, `BidParty`'s Ord, and round → lot_result → sorted winners. That
  is a second copy of the fold's output order, written in SQL, and it would have to follow every
  later fold change.
- Stamping leaves the fold as the only writer of row order. ADR-0017 D1 counts order, and only the
  fold should decide it.
- Option (e), comparing winners in PK order, stays deferred. It would not cover parties or bid
  parties, whose order is served at the head (579 "Served harm").
- Cost: the merge's touched Tenders refold at the next `project`. Merges are run by an operator and
  never scheduled (supervisor.rs: no merge kind appears in the daily or weekly ticks; the weekly
  `org-merge-health` and `scan-org-match-keys` do not repoint).

**D583-2. U1's dry-compare measurement is dropped.**
- The remedy is right whatever the count. A merge whose survivor crosses no sibling's id refolds
  to "verified", so stamping costs a compare and changes nothing.
- The only thing the count would size is U3's cohort. That cohort is settled more cheaply:
  1. Refold 2563 plus project 2564 (2026-10-16 11:34–17:47Z, compare on) re-folded 8,792,804 of
     the 8,797,453 Tenders it planned (538's record, "D7 complete"). The 2026-10-07 all-profile
     refold stamped 8,780,780 Tenders, the whole corpus at the time. So any merge drift from
     before job 2563 was rewritten into the fold's order then, and announced.
  2. Jobs are serial and 2564 ran straight after 2563, so the cohort is the touched Tenders of
     wet merge jobs with id ≥ 2565.
  3. The record shows none. There is no merge kind among the 129 recorded jobs 2629–2757
     (`551-lot-sum/b6/u9/jobs/*.json`, parsed offline). The last altid dry run was 2232 on 10-11
     (518's Status), and 519's last fold was 2347 on 10-12. Jobs 2565–2628 are attributed in the
     record only in part: refresh-org-names 2565/2567/2568, the 552 ship 2570–2572, refold-lot-sum
     dry/wet, refold 2589/2616, and projects.
  4. U3's first step is therefore one free metadata read of `/admin/jobs` (section 6). It decides
     whether there is anything to drain. Prior: nothing.

**D583-3. One shared helper, called once per transaction by all eight callers.**
- All eight callers already collect the loser's Tenders before the repoint (the same
  `parties UNION bid_parties UNION winners` probe), and append one `tender changed` row per Tender
  inside the transaction.
- The helper replaces that append loop and adds the stamp and the requeue. So "announce a
  repointed Tender" and "hand it to the fold" become one call that a future caller cannot do half
  of.
- It is called per transaction, not per loser, so the requeue and stamp run as a few 500-id
  statements, never one per loser. p0's cohort 1–5 run touched 521,148 Tenders in a single job.

**D583-4. No new report fields and no supervisor change.**
- The set the helper stamps is, by construction, the set already counted as `tender_changes`
  ("N tender change event(s)" in every merge summary).
- The merge arms do not auto-queue a `project`. The convention for org-layer jobs is a `project`
  posted by hand right after the wet job, as in dissolve-guid-twins' runbook step 4. That rule is
  written into operations.md (section 4).

**D583-5. No CHANGELOG entry.**
- Precedent: 1fb7541 (579 U4) added none.
- Merges already announce each touched Tender (`tender changed`, issue 286). The follow-up
  correction rows are issue 495's existing announcement, and they now arrive at the next `project`
  instead of at some later refold. `parties[]` order converges to what a fresh projection serves.
  Nothing new to describe for a client.

**D583-6. Deploy class: not a fold change. It may ride the earliest deploy, and it must be live
before the next wet merge.**
- `apply_tenders`, the compare and the projection are untouched. Deploying it re-queues nothing and
  runs no job. It acts only inside a wet merge an operator queues.
- The fast plan (`551-lot-sum/b6/fast-plan.md` §2) lists it with the fold-changing commits for
  deploy #4 after 577 U3 ("it changes refold scope"). That is conservative, but harmless if kept.
  If it rides deploy #4, no P-probe prediction changes, because no merge runs between.
- Hard ordering: deploy 583 U2 **before 519 M6 runs wet**. M6 is a `rekey`/identifier merge, so it
  goes through `repoint_org_references`. The fast plan's paired `refold-lot-sum` admits only
  lot-sum-cohort Tenders, so it does not heal M6's order drift. If M6 runs first, its touched
  Tenders become U3's cohort (section 6, step B).

```rust
/// The merge-side twin of 579 U4 (issue 583): announce the Tenders a merge's repoints
/// touched AND hand them to the fold. Every caller of [`repoint_org_references`] collects
/// the loser's Tenders (party, bid-party and winner rows) before the repoint and calls this
/// once per transaction, inside it:
/// - one seq-less `tender changed` row per Tender (issue 286: what the org-role filters
///   return moved);
/// - the Tenders stamped epoch-stale and their causing notices re-queued (the issue-179
///   pair), so the next incremental fold rewrites them.
///
/// The repoint UPDATEs party, bid-party and winner rows in place, so each keeps the rowid
/// where the loser's id sorted, while the fold writes each group in org-id order and the
/// refold's compare (issue 495) reads rows by position. Left as written, a Tender whose
/// survivor's id sorts across a sibling's is rewritten and announced corrected at its next
/// refold although nothing it binds moved. Stamped here, the next `project` writes the
/// fold's own order and a later refold verifies it. The requeue and the stamp skip their
/// checkpoints inside a transaction (`checkpoint_on`).
async fn announce_repointed_tenders(conn: &Connection, touched: &BTreeSet<i64>, now: i64) -> turso::Result<()> {
    for &tid in touched {
        append_change(conn, "tender", tid, None, "changed", now).await?;
    }
    if touched.is_empty() {
        return Ok(());
    }
    let ids: Vec<i64> = touched.iter().copied().collect();
    let notices = Db::notice_ids_of_tenders(conn, &ids).await?;
    Db::requeue_notice_ids(conn, &notices, false).await?;
    Db::stamp_tenders_stale(conn, ids).await?;
    Ok(())
}
```

  :16365, `stamp_tenders_stale` :16395.

/// After a merge moved the loser onto the survivor: both Tenders stamped stale and their
/// notices re-queued in the merge's own transaction; the trailing fold rewrites the five
/// tables the in-place repoint left out of order (the award's parties, bid parties and
/// winners, the other's parties and bid parties); a later refold with the compare on rewrites
/// none. Unstamped (before issue 583) the trailing fold skipped both Tenders, and that refold
/// rewrote all five, announcing corrections that moved nothing.
async fn assert_merge_reaches_the_fold_fixed_point(db: &store::Db, conn: &turso::Connection) {
    assert_eq!(
        scalar(conn, "SELECT COUNT(*) FROM tender_version_parties WHERE organization_id = 50").await,
        0,
        "the loser's rows moved"
    );
    assert_eq!(
        scalar(conn, "SELECT COUNT(*) FROM tenders WHERE projection_epoch = 0").await,
        2,
        "issue 583: both touched Tenders stamped stale"
    );
    assert_eq!(
        scalar(conn, "SELECT COUNT(*) FROM notices WHERE id IN (900, 901) AND projected = 0").await,
        2,
        "and their notices re-queued"
    );
    let trailing = db.apply_tenders(&[award(KEEP), party_only(KEEP)], NOW, false).await.unwrap();
    assert_eq!(
        (trailing.tenders_corrected, trailing.tables_rewritten),
        (2, 5),
        "the repointed rows put in the fold's order: {trailing:?}"
    );
    db.set_projection_epoch_for_test(-1).await.unwrap();
    let refold = db.apply_tenders(&[award(KEEP), party_only(KEEP)], NOW, false).await.unwrap();
    assert_eq!(
        (refold.tenders_verified, refold.tenders_corrected, refold.tables_rewritten),
        (2, 0, 0),
        "the fold's fixed point: {refold:?}"
    );
}

/// Issue 583: issue 234's merge (one immediate transaction per batch) stamps every Tender its
/// repoint touched; a dry run stamps nothing.
#[tokio::test]
async fn a_provisional_merge_then_a_refold_rewrites_no_table() {
    let (db, conn, path) = seed_583("parity-234", Some("CZ")).await;
    let dry = db.merge_provisional_organizations_batch(100, "", true).await.expect("dry");
    assert_eq!((dry.groups, dry.removed), (1, 1), "{dry:?}");
    assert_eq!(
        scalar(&conn, "SELECT COUNT(*) FROM tenders WHERE projection_epoch = 0").await,
        0,
        "a dry run stamps nothing"
    );
    let wet = db.merge_provisional_organizations_batch(100, "", false).await.expect("wet");
    assert_eq!(
        (wet.removed, wet.mentions, wet.parties, wet.bid_parties, wet.winners, wet.winner_dups, wet.tender_changes),
        (1, 2, 2, 2, 1, 0, 2),
        "{wet:?}"
    );
    assert_merge_reaches_the_fold_fixed_point(&db, &conn).await;
    drop(db);
    for s in ["", "-wal", "-shm"] {
        let _ = std::fs::remove_file(format!("{path}{s}"));
    }
}
