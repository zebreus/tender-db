# 539 post-drain audit: DÖE `published_at` against IssueDate and the export window (read 2026-10-24 02:56–02:57Z)

**Verdict.** The drain did what the rule says, with one exception.
- Inversions (IssueDate civil day > `published_at` civil day) fell from **16,344 to 1**.
  - Before the drain, 128 fetches had at least one inversion. Now only one does.
  - The one left is in fetch 431 (2024-01), profile de-1.1, and both of its dates fall inside the window.
- No fetch's notice count changed.
- The published-day buckets after the drain are **identical** to the pre-drain prediction for option (a)
  (`q20`–`q23`). The comparison is per fetch, profile, bucket and IssueDate-present cell, and 0 notices are off.

## Residual resolved (2026-10-24 03:09Z, owner; 1 statement + 1 GET)

`q30_resid` (plan: SEARCH notices_fetch_id, probed locally on ../plan.db with sqlite3 and turso plan-probe) names the
one remaining row: notice **26250418** (de-1.1, fetch 431). Its published_at is 1705449600 = 2024-01-17T00:00Z,
date-only (`published_has_time` 0), with `published_offset` **-300** (−05:00). Its dispatched_at is
2024-01-17T13:33:51Z, offset 0. The public API serves `published_at` "2024-01-17" and `dispatched_at`
"2024-01-17T13:33:51+00:00", so it is the same day and not an inversion.

The read's civil-day formula `(published_at + offset*60) / 86400` is right for date-only values only when the offset is
positive (notes.md assumed every DÖE offset is). Issue 418 anchors a date-only value at the civil day's 00:00Z, so a
negative offset shifts it to the previous day. This is also why the drain's dry run planned 1,359 de-1.1 rows against
the 1,360 the read measured: the resolver compared the right days. **Real inversions after the drain: 0 of 16,344.**
