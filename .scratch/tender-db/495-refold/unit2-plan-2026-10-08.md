## SDK prepared statements

VERIFIED against the vendored SDK (crates/vendor/turso, wired in by Cargo.toml:147-148 [patch.crates-io]; VENDORED.md: byte-identical to crates.io 0.7.2 except set_query_timeout/interrupt) and the registry turso_core-0.7.2 / turso_sdk_kit-0.7.2. Both plans' SDK claims hold; only small line-number drift (minimal cites connection.rs:103-115; the real query/execute are 108-119).

1. TODAY'S COST
- Connection::query and Connection::execute (connection.rs:108-119) call self.prepare(sql) every time.
- prepare (137-147) goes to TursoConnection::prepare_single (rsapi.rs:1067-1087) and then turso_core Connection::prepare: a full parse and translate per call. This is what unit 2 removes.

2. WHAT A HANDLE IS
- prepare returns `Statement { conn: self.clone(), inner: Arc<Mutex<Box<TursoStatement>>> }` (lib.rs:342-346), which is #[derive(Clone)].
- Statement::execute (lib.rs:428-454): reset, then bind every positional value, then poll step until Done. A Row comes back as Misuse, so SELECTs must use query.
- Statement::query (404-426): reset, bind, then return a Rows that holds a CLONE of the same Statement (rows.rs:6-8).
- TursoStatement::reset (rsapi.rs:1537-1545) is the core reset plus clear_bindings.
- The core reset_internal (statement.rs:1309-1458) always calls Program::abort(None) and releases the active-root and active-writer counters.

3. REUSE INSIDE ONE TRANSACTION: YES
Every execute or query resets and rebinds first.

4. REUSE ACROSS BEGIN IMMEDIATE / COMMIT / ROLLBACK AND THE TRUNCATE CHECKPOINT: YES, already proven in production
- TenderInserts' 7 handles (canonical.rs:15280-15287, 31190-31246) are reused across every batch, COMMIT and checkpoint.
- The write handles among them (tenders, lots, head_update) sit in Done state at COMMIT without tripping StatementsInProgress. So n_active_writes is released at Halt, not at the next reset.
- A schema change re-prepares a handle by itself: at Init (statement.rs:519-528) and in the SchemaUpdated retry loop (547-575).

5. FAILURE SEMANTICS
- abort(None) poisons the transaction only for an unfinished WRITER inside an explicit transaction that has no statement savepoint (vdbe/mod.rs:2516-2531).
- COMMIT and ROLLBACK are refused only while n_active_writes > 0 (vdbe/execute.rs:4163, 4298).
- An undrained SELECT, such as lot_identity's first-row return at canonical.rs:29532, stays counted in n_active_root_statements until its next reset (statement.rs:490-503, 630-634). In WAL mode that blocks neither autocommit (vdbe/mod.rs:1003-1034) nor COMMIT.

6. LIFETIME AGAINST MutexGuard<Connection> (Db::conn, lib.rs:1186)
- A Statement OWNS an Arc clone of the same TursoConnection. It does not borrow the guard, so the compiler will not stop it escaping.
- Drop runs reset_best_effort, then abort, on that shared connection (turso_core statement.rs:1481-1492).
- RULE: create handles only after `let conn = self.conn().await` in apply_tenders, as a LATER-declared local, so they drop first, while the guard is still held. Never put them in Db, a static, a OnceCell or a return value.
- Optional hardening: TenderInserts<'c> with PhantomData<&'c Connection>.

7. ROWS ALIASING
query(&mut self) returns an owned Rows that shares the inner statement. Re-executing the handle while that Rows is alive silently resets the reader. Drain or drop it first. This applies to stored_chain now and to unit 3's compare SELECTs.

8. PARAMETERS ARE MOVED, NOT CLONED
Vec<Value> becomes Params::Positional (params.rs:150), then From<Value> gives rsapi::Value::from_text(String) (vendor value.rs:129-139). Zero String clones; flush_rows' to_vec (canonical.rs:31360) is the only clone today.

9. prepare_cached (connection.rs:150-160, rsapi.rs:1089-1141)
A per-connection cache keyed by SQL text, never evicted, and it still allocates a Statement per call. It is unused in the repo. Not chosen for the hot path; a possible later win for the ~45 non-fold append_change callers.

10. Statement::execute skips maybe_handle_dangling_tx. Harmless: store, ingest and app make no SDK Transaction calls (the grep for .transaction(), unchecked_transaction and prepare_cached is empty).

## Risks
- REVIEW VERDICTS, part 1 (both plans; claims verified at b9906bc).
- All SDK reuse, abort and poison semantics and all canonical.rs anchors in both plans are correct.
- REFUTED (structural): the descriptor as written does not compile. `pub const LEAF_TABLES: [LeafTable; N]` plus `const fn table(self) -> &'static LeafTable { &LEAF_TABLES[self as usize] }` borrows a temporary (E0515). Use the `[&'static LeafTable; N]` const from descriptor_shape.
- REFUTED (structural): 'the tripwire is run_project's 9,000 B budget'. That gauge (supervisor.rs:17588) measures a future that holds the projection as Box::pin (4386, 4401), so it cannot move. The binding guard is poll_once_within("run_project", 472 KiB), measured at 452-458 KiB, so 14-20 KiB of headroom.
- INCOMPLETE (minimal): 'canonical.rs changes do not grow run_spec' is true, but apply_tenders is awaited INLINE at project.rs:3496 and 3605, inside apply_plan_batch and bucketed_fold, which are themselves inline at 1855, 1872, 3379 and 3396 (the 117 KiB frame named at supervisor.rs ~17672).
- Mitigation for both: Box<TenderInserts> AND Box::pin(TenderInserts::prepare(..)). The prepare future holds every built field across its awaits, so a Box<Self> return alone leaves that state inline.
- REVIEW VERDICTS, part 2.
- REFUTED (minimal): the_orphan_sweep_reads_by_index (canonical.rs:31764) is the ORG sweep, not sweep_orphaned_entities.
- SCOPE (minimal): keeping stored_chain as Vec<i64> and deferring lot attribution contradicts issue 495's unit-2 text. Both are read-only or metadata, so they are done now (steps 2 and 7).
- MISSED (both): crates/store/tests/satellite_column_migration.rs already exists and proves Db::open over pre-column satellites, views included.
- MISSED (both): include_str! for a new golden does not compile before the file exists, and GOLDEN_CAPTURE=1 with a broad filter rewrites project_apply.snapshot (project_golden.rs:205-217). Use runtime reads and a distinct variable.
- MINOR (minimal): HashMap<(u8,i64,String),i64> allocates a String per lookup, and clear() is O(capacity). The anchors project_golden :153-155 and snapshot_content are really :178 and :222.
- MINOR (structural): test flush_rows, not Pending, so step 4 does not rewrite the commit-A test.
- BYTES — nothing in steps 1-9 changes logical bytes or change-row order as specified. These are the edits that WOULD:
(a) A descriptor col list out of step with the push-site array, or a wrong Leaf at a push site with equal arity (Texts and Classifications 6; VersionLots, Dates, Parties and BidParties 7; Versions and Bids 8). Values land in the wrong column or table; STRICT catches only type clashes, and NULL-on-NULL is silent. Guarded by the literal pins and both goldens.
(b) Flushing in LEAF_TABLES (teardown) order instead of LEAF_FLUSH_ORDER. Per-table rowids are unaffected, but FK-on store tests fail and the physical page layout differs.
(c) Changing delete order or not keeping tender_versions last. FK-on breaks; freelist reuse differs.
(d) The identity cache: reset at the end rather than the start, kept across Tenders, or consulted after the sweep. That serves stale ids, so wrong entity ids, wrong change entity_ids and possibly missing INSERTs.
(e) Iterating a cache HashMap into writes.
(f) The wrong caused_by_notice_id index in the widened stored_chain. keep becomes 0 or short, so whole chains are rewritten (rowids shift) and extra added/changed/removed change rows appear.
(g) Step 12's ROLLBACK fix changes an error path, so it is filed separately.
- PHYSICAL-ONLY, logical bytes identical. Cache hits change which lookup handle is left mid-row (counted as an active root) at COMMIT and at the TRUNCATE checkpoint. In WAL mode readers block neither (vdbe/mod.rs:1003-1034); at most WAL backfill timing can differ. Prepared plans are fixed at prepare time per apply_tenders call, as conn.execute's are per call.
- Coverage gap until commit A lands. Only project_golden pins output across commits, and it never runs delete_version, stored_chain or the sweep. A keep=0 regression passes every other test, because they compare two runs that share apply_tenders. Commit A must be captured and committed with a production diff of zero.
- Statement lifetime is not compiler-enforced, since a Statement owns a Connection clone. Keep the boxed TenderInserts a local declared after `conn` in apply_tenders, so its Drop (reset, then abort) runs under the guard. Never wrap one prepared-write await in select!/timeout: a suspended writer keeps n_active_writes at 1, ROLLBACK is refused, and apply_tenders' `let _ = ROLLBACK` swallows it.
- Rows aliasing for unit 3. Rows shares its Statement, so re-executing a handle while its Rows is alive silently resets the reader. stored_chain drains to Done; the compare SELECTs must drain before any write (ADR D1.2).
- Identity-cache coherence depends on no entity DELETE or UPDATE between a Tender's first lookup and its sweep. That holds today and under unit 4's leaf-only rewrites. A future writer inside apply_tender_tx that deletes entities breaks it. Guards: reset at the start, debug cross-check on every hit, the documented invariant.
- Migrated PRAGMA arm. Omit FKs in the frozen DDL, as the precedent does, and assert the precondition that the old DDL survived open. If Db::open fails over all 14 pre-column tables at once, that is a real old-DB boot hazard: report it, do not weaken the test. Use GLOB, not LIKE, because LIKE's `_` is a wildcard.
- Prepare surface: about 23 prepares per apply_tenders call instead of 7. That is once per bucket (project.rs:3605) or plan batch (:3496); batch=1 tests pay it per Tender, which is fine. A missing leaf table now fails at prepare time rather than at first delete, which never happens on a Db::open schema.
- Disk. A separate worktree means a cold build and a second ~20-28 GiB artifact family. Check ops/test-gate-disk.sh first, or work in place if no agent is editing canonical.rs. Never pipe the gate; read GATE-EXIT.
