## 3. Hard rules (each one learned the hard way)

**Repo and git**
- **The test gate:** run `ops/check.sh`, never raw `cargo test` (it fills the disk; see CLAUDE.md). Redirect to a file
  and read the echoed `GATE-EXIT=` value: `./ops/check.sh > LOG 2>&1; echo GATE-EXIT=$?`. Never pipe it through
  tail/grep. It takes ~12 min (710 s at `9551a23`). It writes `target/.tests-green = HEAD` only on a CLEAN tree, so do
  not write files into the repo mid-gate; put scratch output in the scratchpad.
- **A focused test mid-iteration** uses the gate's flags AND package set:
  `CARGO_INCREMENTAL=0 CARGO_PROFILE_DEV_DEBUG=0 CARGO_PROFILE_TEST_DEBUG=0 cargo test -p model -p store -p ingest -p tender-db --features tender-db/server <name>`.
- `--features server` is needed to compile `supervisor.rs`, `admin`, `v1`, `webhooks`, `ledger` and `coverage`. A bare
  `cargo check -p tender-db` compiles none of them.
- **Staging:** stage individual files after `git diff <file>`, never `git add -A`. Check the result with
  `git show --stat`.
- **Pushing:** `git push origin HEAD:main HEAD:claude/tender-db-handover-i691vo`, then confirm with
  `git ls-remote --heads origin main`.
- **Commit trailer:** `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` +
  `Claude-Session: https://claude.ai/code/session_…`. No model identifiers anywhere else.
- **The Stop hook** complains about uncommitted or unpushed work at turn end. If code is still mid-gate, push it to the
  handover branch only, and to `main` once green.

**Production**
- **Never run heavy on-box work while ingest/fold jobs run.** The supervisor runs one job at a time; enqueue behind
  the queue, and never kill a running job to get in.
- **Deploy:** `./deploy.sh` (HEAD). Since issue 459 (2026-10-01) the gate is bound to the rev it ships. It skips the

## 6. What you know: the data model, compressed

Read `CONTEXT.md` (glossary and decisions) and `docs/adr/0001…0016`. The essentials:

- **Notices → Tenders.** Every source record is a Notice (immutable, with a content hash; ADR-0001). The projection
  ("project", "the fold") folds notices into versioned canonical **Tenders**. A Tender has `tender_versions` (seq), and
  satellites hang off each version: texts, amounts, classifications, dates, parties, lots, lot_results, bids, contracts,
  winners. Kinds: `procedure`, plus non-procedure publication kinds. A **change log**
  (`changes`, an append-only cursor) feeds SSE, `/v1/changes` and webhooks. `feed_generation` bumps when a wipe
  happens.
- **Classifications** (`tender_version_classifications`): `scheme` is `cpv | nuts | nature`, and `field` is
  `main | additional | place | nature`.
  - CPV is what is bought.
  - NUTS is where it is performed.
  - nature is works/supplies/services/combined (issue 397; codes 1 works, 2 supplies, 3 combined, 4 services).
- **Sources and eras:**
  - TED: eForms XML (sdk versions), the legacy XML eras (r208, r209), and the text era (OJS TXT), plus internal-OJS.
  - DÖE: the sdk-0.1 island and eForms-DE sdk-1.x. Value coverage is low because of what the source publishes (issue
    263). sdk-0.1 is ~0.5% valued, eForms-DE 30–43%, ~15% overall.
  - FTS: OCDS JSON from the UK API (`fts:ocds-1.1`), mapped onto eForms BT ids (`crates/ingest/src/fts`).
  - The ADR-0004 checklists keep each profile's fields mapped-or-ignored and quarantine the unknown.
- **Organizations.** Rows are canonical (with an identifier) or provisional (name only). Identifiers are normalised
  (label prefixes stripped, Greek/Latin confusables folded) and so are names (`name_norm`, plus N2 match keys in
  `org_match_keys` with a genericness wall).
  - **Merge rules**, all recorded in the `org_merge_log(keep, loser, rule, evidence, job_id, at)` ledger:
    - r2: same identifier, with a name gate;
    - e0: same triple, agreeing distinctive keys;
    - p0: provisional echoes;
    - r3;
    - **e2-altid**: an FTS company number and a PPON published together for one supplier (448);
    - **rekey** (453).
  - **Reviewer verdicts** steer the merge arms:
    - `org_merge_verdicts`, keyed (country, scheme, key) with a member set and merge|keep. Schemes include r2,
      `GB:altid` and `GB:rekey`. A HIGH merge verdict admits a pair past the name gate; a keep denies it.
    - `org_name_verdicts`, `org_country_verdicts` and `org_identifier_verdicts` (452: wrong company numbers, withheld
      from matching).
    - case reviews (`/admin/case-reviews`).
  - **The resolver alias:** at fold time, mentions of a merged-away PPON or wrong literal bind to the survivor (448
    unit 3, 453's `applied_literal` chains of up to 8 hops).
- **Job kinds** of the supervisor queue (ADR-0007, `supervisor::run_spec`):
  - fetch, process, project, backfill, fetch-rates, reveal-recheck, analyze;
  - the data-quality report and the census jobs;
  - `match-org-identifiers` (rules `altid`, `rekey`, … with `dry_run`; a wet run holds against the stored dry plan's
    keys, with parity max(2%, 5));
  - the repair-* jobs, sweep-orphan-orgs, and others.
  - A dry plan writes a report you read at `/admin/reports/<kind>`.
- **The read path.** `store::read` builds the list and detail queries. Filtered walks run on an "isolated" pool with
  bounded id bands (issue 408). Engine deadlines: 25 s on REST, 15 s on `/v1/sql`. `ignored_filters` names any filter a
  collection does not apply, and with 455, `resolved_filters` names merged-away org ids.

## 7. Playbook: what worked

- **Measure first, then build.** Size the cohort with a dry run or a bounded read before writing code. Record the
  numbers on the issue.
- **Dry → review → wet, with parity.** Every bulk production write here has a dry plan stored as a report. The wet run
  holds against it, and anything not reviewed waits. When new data lands between the review and the wet run, re-plan,
  diff the keys and review only the delta.
- **Review campaigns** run as Workflows:
  - give the reviewer a rubric file and point it at the cases file by path, not inline arguments;
  - use two independent lenses (register plus skeptic) or a reviewer plus a challenger;
  - admit only on agreement at HIGH, because the safe direction is not merging;
  - check against the Companies House register by curl on
    `find-and-update.company-information.service.gov.uk/company/<n>` (~1.5 req/s; `448-campaign/ch_fetch.py` caches
    it).
- **Write findings into the issue, with dates, job ids and counts.** The next session has nothing else to go on. Keep
  the Status line current and push the history into "Was status:" lines.
- **Fix root causes.** Example: 455 makes ids follow merges, instead of documenting "ids may vanish".
