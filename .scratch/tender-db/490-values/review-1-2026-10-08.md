**Ops review of the issue 490 design: two-deploy rollout with an all-profile refold backfill**

The architecture holds up operationally: nullable columns, the fold as the only writer, no new job type, and the index arriving only after the backfill. The runbook has gaps. The biggest are a lot-row count that is probably far too low, a backfill pass condition that breaks if the refold is stopped, a sizing call that does more than "write nothing", and no check that tender head values survive the refactor. I edited no files and ran nothing on the box.

## Defects and gaps, most important first

**1. The row count used for sizing is probably 3x or more too low, and Q1's way of getting the real count gives the wrong number.**
- The design sizes disk and the index on about 13.2M `tender_version_lots` rows, citing `read.rs:1460`. That figure looks like the lots count:
  - `lib.rs:7799` says "`lots` (13.2M rows on prod)".
  - The test bed in `fixture_selectivity_gate.sh:17` had 40.6M `tender_version_lots` rows against 13.2M lots.
- `tender_version_lots` can never have fewer rows than `lots`. The fold carries every lot forward into every later version (`project.rs:5398-5406`), so the table holds one row per lot per version. 13.2M is a floor, not an estimate. The 2,983-version legacy mega-chain alone adds millions of rows.
- Q1 proposes `SELECT MAX(rowid)`. That is the rowid high-water mark, which full rewrites keep pushing up. `canonical.rs:10240-10246` records about 845M for a table that cannot exceed about 20M rows.
- **Fix:**
  - Read the one-row `sqlite_stat1` entry for `tender_version_lots`. The table is in `ANALYZE_TABLES` (`analyze.rs:35`), and CLAUDE.md and `prod-box-reads.md` treat a one-row stat read as free.
  - Re-size from that number. The full value index is roughly 20–25 bytes per entry, so about 1 GB per 40M rows, not 0.4 GB.
  - Budget disk from refold 2953's measured `df` change and its change-row count, not from the column arithmetic. That change is not recorded in the 484 notes (`484-*.md:644-647`), so record `df` before and after this time.
  - This is not a blocker: about 814 GiB was free after the defrag (`488-*.md:54`).

**2. The backfill pass condition fails if the refold is stopped or restarted, and the equality it asks for can fail without anything being wrong.**
- The design asks for "Tenders written = Tenders stamped, 0 unchanged" on the trailing project.
- A non-rebuild project cannot resume from its plan: `project.rs:1662` sets `resume = rebuild && …`.
- A stopped run commits what it has written and returns (`project.rs:1745-1753`, `1821-1830`). So a stop or a deploy restart means a fresh planning pass of about 4 h. The next run then reports a large `unchanged` count (`canonical.rs:15189-15195`), and the pass condition can never be met. `operations.md:828-833` already warns that resumed folds report differently.
- New tenders created during the fold also make "written = stamped" false without anything being wrong.
- **Fix:** define completeness across runs:
  - the last run finished without STOPPED;
  - the tenders written across all runs since the stamp are at least the number stamped;
  - the last run's `unchanged` count equals what earlier runs of this refold wrote.
  - Also state that no deploy may land during the roughly 10.5 h window.

**3. Nothing checkable on the box records that a tender has been backfilled. The no-bump decision gives up the cheapest way to get that.**
- Normally a bump costs a corpus-wide rewrite and permanent change-feed noise (`canonical.rs:1264-1269`). The all-profile refold pays that cost anyway, because `stamp_stale_for_profiles` (`canonical.rs:8845-8868`) stamps every tender stale.
- What a bump would add: tenders the daily fold touches between deploy A and the refold get a full rewrite instead of an append. That is small.
- What it buys:
  - `projection_epoch = 4` would mean "every version written by 490 code".
  - That can be checked with bounded primary-key window reads.
  - It identifies tenders left behind by a stopped refold.
  - It closes the restored-backup and test-bed hole the design lists as its risk 1.
  - It matches the contract's own wording: "Bump this on any change to the … fold logic" (`:1259`), and this change crosses profiles (`:1283`).
- The catch: with a bump, any whole-corpus walk rewrites every tender. That includes the bucketed path at 100k or more notices, which walks all tenders (2940 walked 8.78M), and 491's 310k-notice drain. A planned walk then becomes the backfill. An unplanned one occupies the queue for about 10.5 h.
- Other jobs (`rederive-eur`, the resolver) stamp epoch 0, so `epoch <> 4` over-reports. That errs on the safe side.
- **Fix:** either bump and use the epoch as the completeness check, or keep no bump, add a `projection_state` completeness flag, and add a "NOT bumped for 490" paragraph next to issue 234's (`canonical.rs:1293-1301`). Today the golden header (`project_golden.rs:111-114`) is the only place the decision would show.

**4. The `expect:1` sizing call is not side-effect free.**
- `"refold" =>` queues the refold and then `project rebuild=false` unconditionally (`supervisor.rs:2109-2113`). Queued jobs have no grouping (`:1218-1243`), so the project runs even after the sizing job aborts. In 484 those were jobs 2041 and 2042.
- If anything is unprojected when you size, that project folds it on deploy-A code. The likely case is 491's pending reparse drain, about 310k notices, which takes the whole-corpus bucketed path (`project.rs:2634`, `3279`; about 4.5 h per `ops.md:540-542`). That delays the real refold by hours.
- **Fix:**
  - Before sizing, confirm nothing is unprojected and the sizing's project finished as a no-op.
  - Or deliberately let 491's reparsed notices ride the real refold, without 491's own project.
  - Correct "writes nothing" in `operations.md:888`.

**5. Nothing checks that tender head values come through deploy A and the refold unchanged.**
- Deploy A swaps the head election's code path (`head_value_eur_cents_with` plus a running partner set), and the refold then re-elects every head (`canonical.rs:15273-15289`). The design's verification reads only lot columns.
- **Fix:**
  - Before deploy A, save the data-quality section-16 band listing. It is a bounded seek on `tenders_current_value_eur` (`ops.md:503-523`).
  - After the refold, require the same heads, apart from daily drift.
  - Unit 1 already captured a free before-image. `m490/data/*.sql.json` has the head values and `*.rest.json` has the REST lot values. Diff the REST files after deploy A to check the `summarise` refactor without touching the box.
  - Those files sit in this session's scratchpad (`/tmp/claude-0/.../scratchpad/m490`), which will not outlive the session. Copy them into `.scratch/tender-db/` now.

**6. The deploy-B measurement plan will probably hit the 408 timeout and gives a misleading comparison.**
- A €1m–€10m `COUNT` joined on the current version is not index-only. Every index entry, for every version, needs a probe into `tenders`. The range holds 984,406 tenders, so that is millions of probes, likely past the 15 s cap.
- If it runs before the boot Reindex finishes (issue 111), it is a full table scan; a bare scan already measured 30.66 s cold (`read.rs:1460`).
- **Fix:**
  - Wait for the Reindex job and confirm the index with a `sqlite_master` read first.
  - Measure top-N and a narrow band with a LIMIT.
  - Do not compare a lot COUNT against the tenders' 56–66 ms.

**7. Q6 resolved: a partial index works only with a literal `IS NOT NULL`, and the full index adds a cost to every future fold.**
- turso 0.7.2 uses a partial index only when the query has a syntactically equivalent term. There is no implication logic; the TODO at `turso_core-0.7.2/src/translate/optimizer/constraints.rs:1280-1322` says so.
- The cost the design misses: indexes are stripped only on a rebuild (`project.rs:1693`), so after deploy B every fold and every future non-rebuild refold maintains the full index for every lot row. About 80% of those entries are NULL, and their positions are random in fold order.
- **Fix:** either record that cost, or ship `WHERE value_eur_cents IS NOT NULL` and put `AND vl.value_eur_cents IS NOT NULL` in the documented recipe.

**8. Deploy A puts mostly-NULL columns on a `v_*` view, which is the stable analyst API.**
- ADR-0015 D3 treats the views as the stable API. Deploy A's `v_lots.value_*` would read NULL for nearly every lot for 10.5 h plus verification, longer if the queue slips.
- Nothing in deploy A needs the view columns: REST still derives the value, and the verification reads the base table.
- **Fix:**
  - Add the `v_lots` projection in deploy B. It costs nothing, because the schema batch recreates every view at boot (`canonical.rs:1086-1096`, `lib.rs:1122`).
  - In deploy A, keep the base-table columns with the transitional note.
  - Add to that note that the columns are unindexed until deploy B, so a `WHERE value_eur_cents …` scans the table and times out.

**9. Rolling back past deploy A after the backfill leaves gaps the runbook doesn't cover.**
- The schema side is safe: the old INSERT names four columns (`canonical.rs:31055`) and the new columns are nullable.
- But any version the old binary rewrites is stored NULL, and re-deploying A never refills it, because kept versions early-return (`canonical.rs:15189-15194`). Deploy B would then serve null for those lots.
- **Fix:** add a runbook line: after any such rollback, run a scoped refold of the affected tenders, or redo the backfill, before deploy B.

**10. (Low) The drain recipe for future rule changes needs a note.**
- The 471-style drain picks tenders by the head value band (`ops.md:584-603`). A rule that refuses more moves only lots whose tender head is already at or above the gate, because the head admits every convertible candidate the lot pick admits. So that part is covered.
- Not covered: the stored values of older versions, which SSE `Scope::At` serves (`sse.rs:468-474`), and any rule that admits more.
- **Fix:** say both in `operations.md`.

## Design claims I checked and found correct

- **Migration:**
  - The nullable ALTER is metadata-only, follows the `MIGRATIONS` precedent, and "duplicate column" errors are swallowed (`lib.rs:691-781`).
  - Creating the view before the ALTER runs works on an existing database; `satellite_column_migration.rs:96-151` pins it for `is_buyer`.
- **Q3:**
  - turso rewrites the stored table SQL on ADD COLUMN (`alter.rs:1414-1422`).
  - That rewrite keeps the composite PRIMARY KEY, the FOREIGN KEYs and STRICT (`schema.rs:3518-3680`), so `drop_and_recreate` (`canonical.rs:10463-10483`) keeps the columns and the primary-key autoindex.
  - The backfill does not touch this path anyway: the full fallback runs with `rebuild=false` (`project.rs:2915-2933`).
- **Stale stamping:** the refold stamps every tender of the listed profiles (`supervisor.rs:5372-5419`). Stale means a full rewrite on every routing path (`canonical.rs:15178-15188`), and the state key is unaffected.
- **Change feed:** a forced rewrite emits a tender "added" at seq 1, an "added" for every lot, plus version and round changes (`canonical.rs:29303-29357`). The design's "more than one per Tender" is right.
- **Bump queues no work:** "a bump queues no work" is correct (`:1264-1266`).
- **Deferred index:** the boot Reindex is queued at the front (`supervisor.rs:3535-3580`). `too_large_to_build` falls back to `COUNT(*)` on the background path (`canonical.rs:10253-10279`), which is acceptable there.
- **SQL surface:**
  - The allow-list works by table name.
  - The `v_lots` columns are appended at the end, so `SELECT *` consumers keep their column positions.
  - No existing column named `value_*` collides with the proposed `("*", …)` notes.
  - The transitional "predates the backfill" clause has precedent (`sql.rs:942-955`).
- **`rederive-eur`:** it is manual and only stamps tenders stale (`supervisor.rs:1458`, `5780-5830`), so the design's rate-lag risk 2 is accurate.
- **Smaller claims:**
  - 900/7 = 128 rows per statement.
  - 10 h 26 m is the right baseline, and the 7.5 h figures at `ops.md:839` and `894` are stale.
  - No new `Spec` arm, so no `run_spec` stack hazard.
  - The plan tests build the deferred indexes (`lib.rs:7550`, `7632`), so a change of plan caused by the new index turns the gate red.
