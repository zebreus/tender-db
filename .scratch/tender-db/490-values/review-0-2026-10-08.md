**Verdict: the election itself is right; the gaps are in rollout and staleness.** A value stored at fold time will equal what `summarise` serves for every lot on a freshly folded database. That holds for ties, currencies without a rate, the no-fallback-to-tender rule, LotsGroup and Part lots, and chains that change later. I found four gaps, all outside the rule. I edited nothing and ran nothing on the box; everything below was read at HEAD `ab879bc`.

## Defects and gaps

**F1 (medium) — deploy B can serve null for Tenders the refold never reached, and the gate cannot tell.**
- **Evidence:**
  - The refold only stamps Tenders that have at least one version caused by a notice in the listed profiles (`canonical.rs:8852-8857`). It only requeues notices with `parse_state = 'parsed'` (`canonical.rs:9137-9138`).
  - An unstamped Tender keeps `projection_epoch = 3` and hits the early return (`canonical.rs:15189-15194`), so its columns stay NULL with nothing to show for it.
  - The design's pass condition is "written == stamped, 0 unchanged". That only checks the cohort that was stamped. It also contradicts the design's own "every Tender written" (§3, Fallback lifetime).
  - Q2 reuses the 24-profile list from 2026-10-07. Any profile ingested since then is missed.
  - The same NULLs come back if a pre-490 binary is ever rolled back to after the refold.
- **Effect:** under deploy B those lots serve `value: null` where REST serves a figure today. NULL already means "no candidate", so no reader can tell the difference.
- **Fix:**
  - Build the profile list fresh at refold time. Seek one distinct profile at a time with the existing next-profile pattern (`canonical.rs:4758-4760`, minus the `'fts;'` bound).
  - Require stamped == the full `tenders` count. After the project, require a windowed `projection_epoch = 0` count of 0.
  - Better: add a durable attestation, `projection_state.lot_values_complete`, following the `currency_presence_complete` pattern (`lib.rs:839-858`). Set it on an empty file and by the backfill. Deploy B keeps the derivation as a fallback, or refuses to switch, while it is 0. A per-row "elected" marker would also work.

**F2 (medium) — after any `rederive-eur`, the stored value stops matching what REST serves today, for an unbounded time.**
- **Evidence:**
  - Today `summarise` reads `tender_version_amounts.eur_cents` live (`read.rs:4031`, `4043`, `4079`), so a rate correction immediately changes which figure the ceiling and scale rule let through.
  - Afterwards the stored pick changes only when the Tender is re-folded. `rederive-eur` only stamps Tenders stale (`supervisor.rs:5815-5822`).
  - Nothing requeues them. The rewrite set is `projected = 0`, never the epoch (`canonical.rs:1264-1265`), and no ingest code reads `projection_epoch`. So the job's message "run `project` to apply" (`supervisor.rs:5840-5843`) is wrong.
  - `tender_version_lots.value_eur_cents` is not in `EUR_LOCI` (`rates.rs:549-554`). In SQL it will then disagree with the winning amount row's `eur_cents`, which falsifies the planned column note ("value_cents in EUR at the version's publication date").
- **What the design says:** Risk 2 covers the lag as out of scope. Note one upside: today a rederive leaves the lot pick on new rates while the head stays on old ones; storing the value makes the two lag together.
- **Fix:**
  - Have `rederive-eur` also requeue the changed Tenders' causing notices. The refold pair's "requeue half" already exists (`notice_ids_of_tenders` at `canonical.rs:8877` and `requeue_notice_ids` at `canonical.rs:8900`; see also the `refold_notices` doc at `canonical.rs:4131-4133`). Make this a precondition of deploy B.
  - Word the column note as "as of the fold".
  - Do not let the verification compare straddle a `fetch-rates` or `rederive-eur`.

**F3 (low) — for an appended version, the fold and today's REST read different copies of the earlier versions.**
- **Evidence:**
  - The fold seeds its running partner set from the in-memory re-fold of the kept versions, `p.versions[..keep]`.
  - `summarise` reads the stored rows of versions up to N (`read.rs:4054-4064`).
  - `keep` compares notice ids only (`canonical.rs:15179-15188`).
  - If the earlier versions were stored by older projection logic with no stale stamp, a 10ᵏ partner can exist in one copy and not the other. The appended version's pick then differs from today.
- **What the design says:** "REST and the fold … differ only in how the inputs are assembled" (§3, Deploy A) understates this. It matches the head election (`head_value_eur_cents(&p.versions, …)` at `:15282`), so it is the more coherent choice.
- **Fix:** nothing to build. After an all-profile refold every version comes from one logic, so the gap is closed. Document it, and expect it as a source of false mismatches if `compare.py` is ever run against a Tender folded incrementally under mixed logic.

**F4 (low) — some rule edits that are read-time only today will need a stamping refold.** A future edit to `sentinel_amount`, `IMPLAUSIBLE_EUR_CENTS` or `ScalePartners` reaches REST lots by deploy today. After 490 it also needs a stamping refold. The design's Risk 3 says so. The `PROJECTION_EPOCH` contract text (`canonical.rs:1259-1262`) does not list the election functions, and the head election already has the same exposure. Add them to that list, and to the golden digest, which the design already extends.

## Claims I checked and found correct

- **The rule.** The proposed `elect_lot_value` matches `read.rs:3989-4092`:
  - candidates are lot-scoped amounts with `quality IS NULL`;
  - sentinels are skipped;
  - the ceiling and the scale rule apply only when an EUR conversion exists;
  - the winner is the highest published cents, compared across currencies, and strict `>` keeps the first of a tie.
  - The €1 bn gate needs no separate check, because `refuses_amount` returns false below `SCALE_ERROR_MIN_EUR_CENTS` (`canonical.rs:2898-2900`).
- **Partners and corroboration.** `of_chain` (`canonical.rs:2853-2880`) builds exactly what `summarise` loads (`read.rs:4054-4076`):
  - partners are every amount of any field, quality or scope, plus every lot award with both cents and currency;
  - corroboration uses all of version N's amounts, and lot awards never corroborate.
  - Stored rows are one-to-one with the facts: plain multi-row INSERTs (`canonical.rs:31055-31067`) and no unique constraint (`:249-252`).
  - The only writers are the fold (`grep`). The only in-place change after writing is `rederive-eur`, which touches only the EUR columns, by rowid (`rates.rs:538`).
- **Ties.**
  - `write_facts` walks the `BTreeSet` (`:29226`); `Fact` derives `Ord` (`:2509`); a lot's amounts are buffered contiguously and flushed in order.
  - The only index on amounts is `(tender_id, seq)` (`:296`). None is deferred, and none exists on `currency`. So rows with equal keys come back in rowid order, which is Fact order: field, then cents, then currency.
- **Currencies without a rate.**
  - Unconvertible figures are kept in both paths.
  - Both convert with `rates.eur_cents` at `civil_date(v.published_at)` through the same `EurContext` (`:3228-3231`, `:28997-29000`).
  - Storing a €0 conversion as NULL affects only the EUR column, not what REST serves.
- **No fallback to the tender figure.** `summarise` filters `s.lot_id IS NOT NULL`. Tender-scope amounts only feed the partner set and corroboration, and `add_version_figures` and `set_head` include them.
- **LotsGroup and Part.** Neither `summarise` nor `write_version` looks at `kind`. Lot identities created only by group membership or results (`:29019-29032`, `result_lot` at `:29085`) never get a `tender_version_lots` row, so they are never served. No divergence.
- **Chains that change later.**
  - Version N's pick reads only versions up to N.
  - The running partner set (kept prefix, then each rewritten version, with `set_head` per version and a final `set_head` for a shrunk chain) reproduces `of_chain` of each prefix.
  - `p.versions` is always the whole chain (`project.rs:3408-3414`, `3910-3916`).
  - A stale stamp forces `keep = 0`.
- **The state key and early return are untouched.** Change rows diff in-memory structs (`:29303-29357`), never stored columns.
- **Storing per version is needed.** `summarise` does run at non-head versions, for the SSE `Scope::At` payload (`sse.rs:468-474`).
- **The refold does not touch Q3.** The full fallback is `rebuild=false` (`project.rs:1685-1690`), so `drop_and_recreate` is not on the backfill path.
- **Creating the view before the ALTER works.** `satellite_column_migration.rs:98-151` pins the precedent.
