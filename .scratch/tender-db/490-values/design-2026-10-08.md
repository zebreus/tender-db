# Issue 490 implementation design: store the elected lot value at fold time

I edited no files and ran nothing on the box. I checked the readers' anchors against the current tree (HEAD `ab879bc`). All line numbers below are from that tree.

## Decision summary

- **Storage:** add three nullable columns to `tender_version_lots`: `value_cents`, `value_currency`, `value_eur_cents`. Each version row stores its own value.
- **Writer:** the fold is the only writer. It calls one new function, `canonical::elect_lot_value`. `ScalePartners` is refactored so a running partner set is built once per Tender, not per version.
- **Rollout:** two deploys.
  - Deploy A: the fold writes the columns and `v_lots` exposes them. `summarise` still derives the value, but through the same `elect_lot_value`, so REST output does not change.
  - Between the two: one all-profile `refold`, about 10.5 h, then a verification read on windows.
  - Deploy B: `summarise` reads the columns, and the read-time derivation is deleted. The value index is added as a deferred index.
- **Fallback:** none in the final code. The derivation lives only between deploy A and deploy B.
- **`PROJECTION_EPOCH`:** no bump.
- **`/v1/lots?min_value=`:** stays on the tender head.

## 1. Storage shape

### Columns

Add them to the `CREATE TABLE` at `crates/store/src/canonical.rs:217-224`, and in the same commit add three `MIGRATIONS` lines in `crates/store/src/lib.rs`. The array is declared `[&str; 30]` at :691; it becomes 33. Put the new lines after the `is_buyer` line at :771.

```sql
value_cents     INTEGER, -- the elected figure as published; NULL = no lot-scoped figure survives
value_currency  TEXT,    -- NULL exactly when value_cents is
value_eur_cents INTEGER  -- value_cents in EUR at the version's publication date
```

Each column is nullable with no default, so adding it is metadata-only (the `alter_add_column_cost.rs` and `is_buyer` precedent).

### What NULL means

- `value_cents` and `value_currency` are both set or both NULL. Both NULL means no lot-scoped candidate survived the election. The lot does not fall back to tender-scoped amounts, exactly as `summarise` behaves today (`read.rs:3989-3997` filters `s.lot_id IS NOT NULL`).
- `value_eur_cents` is NULL when there is no value, or when the winner has no rate. Unconvertible winners are still elected, because REST serves the published figure.
- **Decision to confirm:** a conversion that rounds to €0 is also stored as NULL here.
  - This is the issue-378 vocabulary rule from `head_value_eur_cents` (`canonical.rs:2689-2708`).
  - It only touches sub-half-cent figures such as HUF 1.48. The `value_cents`/`value_currency` pair still carries the figure, so REST output does not change.
- During deploy A, before the backfill, NULL also means "row not yet written by 490 code". REST does not read the columns until deploy B, so this ambiguity never reaches REST.

### Why per version, on `tender_version_lots`

- **It matches how `summarise` keys rows.** The primary key `(tender_id, seq, lot_id)` is exactly `summarise`'s row key (`read.rs:3921-3922`).
- **Historical versions are read.** SSE `include_data` reads `Scope::At{seq}` for non-head versions (`sse.rs:468-474`). A head-only column on `lots` could not serve those reads.
- **Kept versions stay valid.** The pick for version N reads only versions 1..=N and the rates at N's date. A kept version has the same notice ids at the same positions under the same epoch (`canonical.rs:15178-15188`), so its value cannot change when N+1 arrives. That is the point where the `ScalePartners` doc objection (`canonical.rs:2804-2812`, a per-`Fact` marker over the whole chain) does not apply.
- **The state key is untouched.**
  - `stored_chain` reads only `caused_by_notice_id` (`:15432-15444`).
  - Change rows diff the in-memory structs in `append_version_changes` (`:29303-29357`), never stored columns.
  - So the early return at `:15189-15194` and `keep` are the same with or without the columns.

### Index (deploy B only, deferred)

- Add `("tender_version_lots_value_eur", "tender_version_lots(value_eur_cents, tender_id, seq, lot_id)")` to `DEFERRED_TENDER_INDEXES` (`canonical.rs:10327`, `[…; 19]` becomes 20). The model is `tenders_current_value_eur` at `:10412-10417`.
- It is covering, so a top-N or range query probes only `tenders` by primary key to check that the row is the current version.
- It ships in deploy B, after the backfill. It is built once, sorted, by the boot-time Reindex (`missing_deferred_indexes` `:10295` → `Supervisor::ensure_deferred_indexes`, `supervisor.rs:3535-3580`). The refold therefore does not maintain it with random writes.
- Without it, a corpus-wide value range on lots is a scan of about 13.2M rows. A bare scan of that table was measured at 30.66 s cold (`read.rs:1453-1457`), so it would time out.

### `/v1/lots?min_value=`

**Not switched.** It keeps comparing `tenders.current_value_eur_cents` (`read.rs:3374`, `3575-3576`).

- Unit 1 found that 3,176 of 6,297 current lots have no lot-scoped amount while their tender has one, and the 2021 r209 era projects no lot amounts at all.
- A lot-level bound would silently drop about half of today's matches. That is a contract change needing a CHANGELOG entry and its own plan measurement.
- Record this in the issue as decided. File a follow-up only if a consumer asks for a lot-level bound.

### (b) One election function, beside `head_value_eur_cents` (`:2650`)

```rust
pub struct LotAmount<'a> { pub field: &'a str, pub cents: i64, pub currency: &'a str,
                           pub eur_cents: Option<i64>, pub quality: Option<&'a str> }

/// The per-row skips (issue 372 withheld, 366 sentinel, ceiling only where a conversion exists).
pub fn lot_amount_admissible(a: &LotAmount) -> bool {
    a.quality.is_none() && !sentinel_amount(a.cents)
        && !a.eur_cents.is_some_and(|e| e > IMPLAUSIBLE_EUR_CENTS)
}

/// Issue 490: THE elected value of one lot of one version. Candidates in Fact order
/// (BTreeSet order = the rowid order summarise scanned); max PUBLISHED cents, strict `>`
/// so the first of a tie wins; scale rule only where eur_cents exists. `partners` must be
/// of_chain(chain[..=N]) for version N.
pub fn elect_lot_value<'a>(amounts: impl IntoIterator<Item = LotAmount<'a>>,
                           partners: &ScalePartners<'_>) -> Option<LotAmount<'a>> {
    let mut best: Option<LotAmount<'a>> = None;
    for a in amounts {
        if !lot_amount_admissible(&a) { continue; }
        if a.eur_cents.is_some_and(|e| partners.refuses_amount(a.field, a.currency, a.cents, e)) { continue; }
        if best.as_ref().is_none_or(|b| a.cents > b.cents) { best = Some(a); }
    }
    best
}
```

This reproduces every behaviour of `read.rs:4022-4092`:

- raw-cents ranking across currencies;
- unconvertible amounts admitted;
- €0 conversions admitted as candidates (only the stored EUR is NULLed, per §1);
- the gate is implicit, because `refuses_amount` returns false below €1 bn (`:2898`);
- the first row wins a tie.

### (c) Running partner set in `apply_tender_tx`

The write loop is at `:15224-15232`.

- Before the loop: `let mut partners = ScalePartners::new(); for v in &p.versions[..keep] { partners.add_version_figures(v); }`. This is in memory only, with no I/O.
- In the loop, before `write_version`: `partners.add_version_figures(version); partners.set_head(version);`.
- After the loop: `if let Some(h) = p.versions.last() { partners.set_head(h) }`.
  - This is required: when the chain shrank and `keep == p.versions.len()`, the loop body never runs and the head map would be empty.
- Then `head_update` (`:15282`) calls a new `head_value_eur_cents_with(head, &partners, &rates)`.
  - `head_value_eur_cents(chain, rates)` keeps its signature and becomes `head_value_eur_cents_with(chain.last()?, &ScalePartners::of_chain(chain), rates)`. Its unit tests at `:31604-32067` keep calling it.
  - This removes the second whole-chain pass, so the fold's cost grows only by the per-version `set_head`, which is proportional to rows already written. It avoids the quadratic `of_chain` per prefix that the 2,983-version legacy mega-chain would hit.

### (d) Thread the partner set into `write_version`

`write_version` is at `:28974`. Its only caller is `:15228`.

- Add a parameter `partners: &ScalePartners<'_>`.
- Add `fn eur(&self, cents, currency) -> Option<i64>` to `EurContext` (`:3228`), and make `cents()` call `opt_int(self.eur(..))`. The amount row and the lot value then use one conversion.
- In the lot loop (`:29003-29012`):

```rust

```

### (e) Widen the flush

In `Pending::flush` (`:31055`) the statement becomes `INSERT INTO tender_version_lots(tender_id, seq, lot_id, kind, value_cents, value_currency, value_eur_cents) VALUES ` with a column count of 7. That gives 128 rows per statement under `MAX_BATCH_BIND`, down from 225.

Also correct the `Pending` and `write_facts` comments (`:31009-31021`, `:29211-29213`): amount row order IS observable through the lot tie-break. It is now pinned by Fact order, not left to scan order.

## 7. Risks

1. **Deploy B shipped onto a DB that was not refolded** (a restored backup, an old test bed) serves null lot values for every unrefolded Tender. Gate deploy B on the refold's counts line and say so in `operations.md`.
2. **Rate corrections lag.** `rederive-eur` updates `eur_cents` in place and only stamps Tenders stale (`supervisor.rs:5815-5822`). Stored lot values, and the edge cases that depend on EUR (ceiling, gate), then lag exactly as `current_value_eur_cents` already does. Today REST reacts immediately. Since nothing requeues stale-stamped Tenders, that existing gap now covers lot values too. The follow-up is for `rederive-eur` to requeue its changed Tenders' notices; it is out of scope here.
3. **A future rule change** (for example issue 492's k = 2) becomes a drain. It already is one for the head. `refold-notices` stamps stale, so kept versions are rewritten too.
4. **Tie-break.** Equivalence rests on flush preserving Pending (Fact) order, which is the rowid order REST scans. Only exact-cents, mixed-currency lot ties can differ; the unit-1 windows had none. The verification compare will catch any.
5. **Coverage gaps:**
   - Lot awards are not elected, so r209 2021 lots are NULL. 6941544's £80 bn award is still served raw in `v_lot_results`.
   - The lot value ranks by published cents, so `value_eur_cents` is not necessarily the lot's largest EUR value.
   - The docs must state both.
6. **Queue time.** The refold needs a 10.5 h queue gap, and another job is running now. Issue 491's pending drain (reparse 12 fetches, then about 310k notices on the 4.5 h bucketed path) could be folded into this refold if its reparse lands first.
7. **Index planner risk.** Until the weekly `analyze` the new index has no statistics, so check with `plan-probe` that the primary-key-prefix reads of `tender_version_lots` are not re-planned onto it.
